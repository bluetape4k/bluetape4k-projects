# Issue #1888: Kafka branching 테스트의 준비·전송·정리 경계를 명시한다

## 맥락

Issue [#1888](https://github.com/bluetape4k/bluetape4k-projects/issues/1888)은
Kafka3와 Kafka4의 동일한 `KafkaStreamsBranchTests`가 비동기 전송 직후
출력 topic을 읽어 flaky하게 실패한 문제를 추적한다. live CI run
`42493199865`와 재시도 run `42499928139`에서 true branch가 두 건 대신 한
건만 관측됐다.

## 원인과 결정

- Spring Kafka Streams를 `RUNNING` 상태까지 기다린 뒤 consumer를 구독하고
  메시지를 전송한다.
- 각 `sendDefault` future를 bounded `get(60, TimeUnit.SECONDS)`로 기다려
  producer ack와 stream 입력 순서를 확보한다.
- true/false 출력의 `getRecords`에 각각 `minRecords = 2`, `minRecords = 1`을
  명시해 부분 poll을 성공으로 취급하지 않는다.
- 두 consumer는 Kotlin `use` 블록으로 감싸 assertion 실패 때도 close한다.
- Kafka3와 Kafka4 테스트는 동일한 lifecycle 계약을 유지하고 무거운 검증은
  순차적으로 실행한다.
- Python 회귀 계약은 두 파일에서 `stop → listener → start → RUNNING await`
  순서와 두 consumer의 `minRecords` 적용 위치까지 확인한다.

## 검증

- RED: 기존 소스에서 Streams readiness, producer ack, 최소 record 수, `use`
  cleanup을 요구하는 회귀 계약이 양쪽 모두 실패했다.
- GREEN: 동일 회귀 계약 통과
- lifecycle 순서·consumer 수·record-count 위치를 포함한 강화된 회귀 계약도
  통과
- `:bluetape4k-kafka:test --tests org.springframework.kafka.streams.KafkaStreamsBranchTests`
  — 1 passing
- `:bluetape4k-kafka4:test --tests org.springframework.kafka.streams.KafkaStreamsBranchTests`
  — 1 passing
- Kafka3/Kafka4 모듈 Detekt — BUILD SUCCESSFUL. 기존 테스트 파일의
  SerialVersionUID/MaxLineLength 등 경고는 touched path 밖에 남아 있다.
- `python3.13 -m unittest tests.test_catalog_workflows` — 146개 통과
- `git diff --check` — 통과

## 놓치기 쉬운 점

producer future가 완료됐다는 사실만으로 downstream branch record가 이미
poll됐다는 뜻은 아니다. Streams `RUNNING` readiness와 consumer의 최소 record
수 조건을 함께 유지해야 부분 poll을 성공으로 오인하지 않는다.

## 다음 변경자를 위한 guard

Kafka3/Kafka4 테스트를 수정할 때는 두 파일을 함께 비교하고, readiness,
bounded send acknowledgement, expected minimum records, 예외 안전 cleanup을
모두 유지한다. hosted Kafka matrix가 새 exact head에서 재실행되기 전에는
기존 retry-green 결과를 최종 안정성 증거로 승격하지 않는다.
