### 수정 완료

- `CompletableFuture.join(Duration)`가 원인 예외를 `ExecutionException`으로 감싸던 동작과 default overload가 완료된 `null`을 보존하던 동작을 회귀 테스트로 고정했다. timeout API는 `(long, Function0)`과 `(long, ExecutorService, Function0)` 두 JVM overload를 유지하고 executor의 종료 계약을 문서화했다. 근거는 `CompletableFutureSupport.kt`, `TimeoutSupport.kt`, `FutureCompatibilityTest.kt`, `TimeoutSupportTest.kt`다.
- `FutureSupport`는 timeout=0, 외부 취소, iterable 취소에서 미완료 source future를 best-effort로 취소하고 원래 cancellation을 다시 던지도록 수정했다. 원격 작업 취소를 보장하지 않는다는 API 경계도 KDoc에 명시했다.
- Lettuce·Hazelcast·Redisson의 suspend adapter는 동기식 호출을 IO dispatcher에서 실행한다. Redis codec 기본값은 기존 LZ4 Fory payload를 읽는 형식으로 돌리고, FastFory는 명시적 선택으로 남겼다. `trustedInternal()`의 fallback 기본값도 기존 Kryo5 형식으로 복원했다.
- Lettuce Deflate codec factory의 KDoc은 `deflateFastFory()`와 `deflateFory()`가 실제 사용하는 serializer 이름과 일치하도록 바로잡았다.
- 삭제됐던 CBOR/Ion/Smile Jackson 2·3 facade를 복원했다. NearJCache는 Java consumer ABI fixture를 두고, 기존에 비활성화된 문서/API 계약 테스트 6개를 다시 활성화했다.
- CI와 nightly/examples workflow의 demo task 이름·결과 경로를 이동 후 실제 project 경로에 맞췄다. JVM release contract 검사는 Markdown 표 공백에 기대지 않고 version cell 의미를 확인하도록 바꿨다.
- `checkDisabledTests`가 기록하는 알려진 결함은 다시 활성화된 테스트로 제거했다. `DisabledTestReportTask.sourceFiles`를 task-managed abstract property로 바꿔 task가 `Project`를 캡처하지 않게 했다.
- 영향받은 production/test 줄의 Detekt finding을 수정하거나 동작 근거가 있는 좁은 suppression으로 한정했고, 전체 재실행 후 PR 추가 Kotlin 줄 finding 0건을 확인했다.
- gRPC port validation의 공개 inline 함수는 `@PublishedApi internal` 범위 상수만 참조하도록 정리했다. 첫 `testClasses` 실행에서 발견된 compiler visibility 오류를 수정했고, gRPC production compile 및 전체 test source compile을 다시 통과했다.

### 잔여 한계

- 저장소에는 전체 공개 API를 이전 baseline과 비교하는 전역 `checkBinaryCompatibility` task/API dump가 없다. 따라서 이번 변경의 구체적인 ABI 위험은 `FutureCompatibilityTest`, NearJCache의 컴파일된 Java consumer fixture, serializer facade 호환성 테스트, compressor ByteBuffer ABI fixture로 검증했다. 이 증거는 변경하지 않은 모든 공개 JVM 타입의 완전한 ABI diff를 대신하지 않는다.
- root compile-only build는 성공했지만 `jibDockerBuild` 두 태스크가 Gradle configuration cache에 호환되지 않아 캐시 항목은 폐기된다. 직접 Jib workflow는 기존대로 `--no-configuration-cache`를 사용한다. 이 문제는 빌드 실패를 만들지 않았고 이번 변경에서 Jib task 동작은 바꾸지 않았다.
- root Detekt는 성공했으며 선택한 모듈의 기존 finding은 남아 있지만 PR 추가/수정 행의 신규 finding은 0건이다.
